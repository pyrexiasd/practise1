# Практическая работа № 1. Локальный Lakehouse и TPC-H Q3

## 1. Вариант и масштаб

| Поле | Значение |
| --- | --- |
| ФИО (как в VK Education) | Черечуев Артем Васильевич |
| Вариант | Q3 «Shipping Priority» |
| Масштаб | sf10 |
| Почему этот масштаб | На sf10 в lineitem около 60 млн позиций. Этого хватило, чтобы сравнить размер файлов и время запросов на одном ПК. Во всех слоях и замерах использовал один масштаб. |

## 2. Поднятые сервисы и почему именно они

| Сервис | Роль | Почему выбрал |
| --- | --- | --- |
| Silo  | Хранит файлы данных и метаданные Iceberg. | Trino и Spark читают файлы из одних бакетов по S3 API. В браузере можно посмотреть, какие файлы записались. |
| PostgreSQL  | Хранит каталог Lakekeeper. | Дефолтный backend для lakekeeper. |
| Lakekeeper  | Даёт движкам общий каталог таблиц Iceberg. | Удобный общий REST-каталог, позволяет не плодить сущности. Таблицу, которую создал в Trino, можно открыть в Spark . |
| Trino  | Читает TPC-H, собирает слои и выполняет Q3. | В нём есть нужные коннекторы TPC-H и Iceberg. |
| Apache Spark  | Читает Bronze из отдельного контейнера. | Нужен, чтобы проверить видит ли он ту же самую таблицу в соседнем контейнере. |

## 3. Разбор запроса — какие данные нужны

Q3 ищет десять заказов сегмента BUILDING с наибольшей выручкой по позициям, отгруженным после 15 марта 1995 года. Заказы должны быть оформлены до этой даты.

| Таблица | Колонки | Как использую |
| --- | --- | --- |
| `customer` | `custkey`, `mktsegment` | Нужен, чтобы отфильтровать сегмент BUILDING. Ну и по custkey соединяем клиентов с их заказами.. |
| `orders` | `orderkey`, `custkey`, `orderdate`, `shippriority` | Тут фильтруем всё по дате заказа и связываем таблицы между собой. Саму дату и приоритет потом  передаем в итоговую витрину. |
| `lineitem` | `orderkey`, `linenumber`, `extendedprice`, `discount`, `shipdate` | Связываю позиции с заказом, фильтруем по дате отгрузки и считаем выручку(уже со скикдкой). `linenumber` чтобы строки в Silver нормално различались. |

## 4. Медальон — решения по каждому слою

Размеры в таблицах из сохраненого прогона. Чтобы посчитать объем, сложил `file_size_in_bytes` из Iceberg `$files`, перевел в мБ . Строки посчитал через `COUNT(*)`. Parquet с ZSTD выбран по замерам Bronze. Для Silver и Gold использовались те же настройки записи.

### Bronze

| Таблица | Колонки | Строк | Вес, МиБ | Формат | Сжатие | Партиции | Обоснование |
| --- | --- | ---: | ---: | --- | --- | --- | --- |
| `bronze.q3_sf10.customer` | `custkey, mktsegment` | 1 500 000 | 1,9777 | Parquet | ZSTD | Нет | Из-за дублей в сегментах компрессия отрабатывает отлично. Вся таблица легла в один файл. |
| `bronze.q3_sf10.orders` | `orderkey, custkey, orderdate, shippriority` | 15 000 000 | 81,7637 | Parquet | ZSTD | Нет |В запросе Q3 берется сразу несколько лет, так что делать партиции по дням не было смысла. Без них данные разбились на 4 файла. |
| `bronze.q3_sf10.lineitem` | `orderkey, linenumber, extendedprice, discount, shipdate` | 59 986 052 | 392,4998 | Parquet | ZSTD | Нет | Для Q3 нужен большой разброс по датам отгрузки. Партицировать тоже не стал, на выходе получилось 15 parquet-файлов, сжатых ZSTD. |

### SQL для Bronze, Silver и Gold

```powershell
@'
SET SESSION bronze.compression_codec = 'ZSTD';
SET SESSION silver.compression_codec = 'ZSTD';
SET SESSION gold.compression_codec = 'ZSTD';

CREATE SCHEMA IF NOT EXISTS bronze.q3_sf10;
CREATE SCHEMA IF NOT EXISTS silver.q3_sf10;
CREATE SCHEMA IF NOT EXISTS gold.q3_sf10;

CREATE TABLE IF NOT EXISTS bronze.q3_sf10.customer
WITH (format = 'PARQUET') AS
SELECT custkey, mktsegment
FROM tpch.sf10.customer;

CREATE TABLE IF NOT EXISTS bronze.q3_sf10.orders
WITH (format = 'PARQUET') AS
SELECT orderkey, custkey, orderdate, shippriority
FROM tpch.sf10.orders;

CREATE TABLE IF NOT EXISTS bronze.q3_sf10.lineitem
WITH (format = 'PARQUET') AS
SELECT orderkey, linenumber, extendedprice, discount, shipdate
FROM tpch.sf10.lineitem;

CREATE TABLE IF NOT EXISTS silver.q3_sf10.shipping_lines
WITH (format = 'PARQUET') AS
SELECT
    l.orderkey,
    l.linenumber,
    o.orderdate,
    o.shippriority,
    l.shipdate,
    l.extendedprice * (1 - l.discount) AS net_revenue
FROM bronze.q3_sf10.customer AS c
JOIN bronze.q3_sf10.orders AS o ON c.custkey = o.custkey
JOIN bronze.q3_sf10.lineitem AS l ON l.orderkey = o.orderkey
WHERE c.mktsegment = 'BUILDING'
  AND o.orderdate < DATE '1995-03-15'
  AND l.shipdate > DATE '1995-03-15';

CREATE TABLE IF NOT EXISTS gold.q3_sf10.shipping_priority
WITH (format = 'PARQUET') AS
SELECT orderkey, sum(net_revenue) AS revenue, orderdate, shippriority
FROM silver.q3_sf10.shipping_lines
GROUP BY orderkey, orderdate, shippriority
ORDER BY revenue DESC, orderdate, orderkey
LIMIT 10;
'@ | docker compose exec -T trino trino --file /dev/stdin
```

Сверил все 10 строк с прямым Q3 на `tpch.sf10`. Выручка округляна до четырёх знаков, чтобы убрать погрешность суммирования. При равной выручке строки упорядочены по дате и ключу заказа.

### Сверка Gold с прямым Q3

```powershell
$q3 = @'
SELECT
    l.orderkey,
    sum(l.extendedprice * (1 - l.discount)) AS revenue,
    o.orderdate,
    o.shippriority
FROM {source}.customer AS c
JOIN {source}.orders AS o ON c.custkey = o.custkey
JOIN {source}.lineitem AS l ON l.orderkey = o.orderkey
WHERE c.mktsegment = 'BUILDING'
  AND o.orderdate < DATE '1995-03-15'
  AND l.shipdate > DATE '1995-03-15'
GROUP BY l.orderkey, o.orderdate, o.shippriority
ORDER BY revenue DESC, o.orderdate, l.orderkey
LIMIT 10
'@
$reference = $q3.Replace('{source}', 'tpch.sf10')

$expected = docker compose exec -T trino trino --output-format TSV --execute @"
SELECT orderkey, round(revenue, 4), orderdate, shippriority
FROM ($reference) AS q3
ORDER BY revenue DESC, orderdate, orderkey
"@

$gold = docker compose exec -T trino trino --output-format TSV --execute @'
SELECT orderkey, round(revenue, 4), orderdate, shippriority
FROM gold.q3_sf10.shipping_priority
ORDER BY revenue DESC, orderdate, orderkey
'@

$gold
Compare-Object $expected $gold -SyncWindow 0
```

`Compare-Object` выводит только расхождения. Если после десяти строк Gold ничего больше нет, результаты совпали.

## 5. Тесты производительности

Сделал два одинаковых набора таблиц для Bronze в Parquet. Один сжал GZIP, второй — ZSTD. Прогнал на обоих Q3 и сверил результат с исходным запросом. Потом повторил замеры для ORC.

В таблицах указана медиана трёх прогонов после первого. Время взял из `elapsedTimeMillis` в Trino. Размер — сумма размеров файлов трёх таблиц.

| Сжатие на Bronze | Время запроса, с | Размер Bronze, МБ | Вывод |

| GZIP | 2,664 | 503,57 | Q3 быстрее на 0,225 с. Запись заняла 35,594 с. |

## 6. Часть 2 — осмысление и работа с инструментами

### 6.1. Понять и объяснить

| Вопрос | Ответ |
| --- | --- |
| Зачем нужны большие данные и lakehouse? | Большой объём истории заказов позволяет анализировать выручку и отгрузки за разные периоды. Файлы лежат в объектном хранилище отдельно от движков, поэтому Trino и Spark читают одну копию данных. Iceberg хранит схему и версии таблиц. PostgreSQL в этом стенде обслуживает каталог. |
| Что произошло после изменения схемы Silver? | `ALTER TABLE silver.q3_sf10.shipping_lines ADD COLUMN shipping_note VARCHAR` добавил необязательное поле. У всех 302 114 существующих строк в нём `NULL`. Список путей из `shipping_lines$files` до и после изменения совпал. |
| Как вернуть данные из снапшота? | На отдельной таблице `silver.demo.q3_sf10_snapshot` проверил удаление и откат. После удаления осталось 0 строк. Запрос к сохранённой версии показал 5 строк, а после отката 5 строк снова доступны обычным запросом. |

Сравниваю пути файлов до и после добавления столбца. Для отката создаю отдельную таблицу из пяти строк. ID снапшота получаю перед удалением и подставляю в обе команды.

#### Изменение схемы Silver

```powershell
docker compose exec -T trino trino --execute @'
SELECT file_path FROM silver.q3_sf10."shipping_lines$files";
ALTER TABLE silver.q3_sf10.shipping_lines ADD COLUMN IF NOT EXISTS shipping_note VARCHAR;
SELECT file_path FROM silver.q3_sf10."shipping_lines$files";
SELECT count(*) AS rows, count(shipping_note) AS filled_notes FROM silver.q3_sf10.shipping_lines;
'@
```

#### Чтение снапшота и откат

```powershell
docker compose exec -T trino trino --execute @'
CREATE SCHEMA IF NOT EXISTS silver.demo;
DROP TABLE IF EXISTS silver.demo.q3_sf10_snapshot;
CREATE TABLE silver.demo.q3_sf10_snapshot WITH (format = 'PARQUET') AS
SELECT orderkey, linenumber, net_revenue
FROM silver.q3_sf10.shipping_lines
ORDER BY orderkey, linenumber
LIMIT 5;
'@

$snapshot = docker compose exec -T trino trino --output-format TSV --execute @'
SELECT snapshot_id FROM silver.demo."q3_sf10_snapshot$snapshots"
ORDER BY committed_at DESC LIMIT 1
'@

docker compose exec -T trino trino --execute @"
DELETE FROM silver.demo.q3_sf10_snapshot;
SELECT count(*) FROM silver.demo.q3_sf10_snapshot;
SELECT count(*) FROM silver.demo.q3_sf10_snapshot FOR VERSION AS OF $snapshot;
ALTER TABLE silver.demo.q3_sf10_snapshot EXECUTE rollback_to_snapshot($snapshot);
SELECT count(*) FROM silver.demo.q3_sf10_snapshot;
"@
```

### 6.2. Подключение Spark к Lakehouse

| Инструмент | Почему выбрал |
| --- | --- |
| Apache Spark 3.5.3 | Подключается к Iceberg REST и читает Parquet из того же S3-хранилища. Нужен, чтобы проверить видит ли он ту же самую таблицу в Trino. |

Spark подключается к REST-адресу Lakekeeper и читает файлы из Silo через S3FileIO. Через `spark-sql` выводим список таблиц Bronze, первые пять клиентов и число строк в `bronze.q3_sf10.customer`.

## 7. Выводы

Архитектура медальон удобна тем, что позволяет поэтапно обрабатывать данные, не теряя исходные. Мы идем от сырой копии(Bronze) к очищенным(Silver), а уже потом к готовой витрине(Gold). Iceberg REST показал, как можно отвязать метаданные от конкретной СУБД, можно параллельно читать одну таблицу разными движками, это удобно и быстро. В тестах форматов сжатия понял, что нужно выбирать между скоростью и размерами. ORC + ZSTD работал быстрее всего на моих данных, Parquet + ZSTD сжимает лучше. В итоге я выбрал Parquet + ZSTD, т.к поставил в приоритет экономию данных, удобно использоват тот или инной метод взависимости от твоих потребностей.
